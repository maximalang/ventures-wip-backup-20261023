# Продуктовая ставка и native handoff

Используй для продуктовой гипотезы, не для каждой технической операции. Kanban — единственный реестр; отдельная receipt-schema и consumer не требуются.

В исходной карте достаточно:
- гипотеза, пользователь, ожидаемая польза;
- baseline/источник и условие успеха или остановки;
- срок наблюдения, один accountable;
- факт/источник, неизвестное и continue/iterate/kill.

Финансовый evidence: scope, период, валюта и источник. Выручка, возвраты, затраты, обязательства и оценки отдельно. Неизвестное = null с причиной, не ноль. Мандат/finance gates — по APPROVALS.md.

Закрывай фазу поддержанным native complete/request-review, сохраняя в summary/metadata результат, evidence, оставшееся ограничение и конкретного следующего owner/ref. Не удерживай готовую фазу открытой до выручки. Follow-up нужен только для реальной незавершённой работы.

Parent edges — реальные prerequisites, не принадлежность ставке. Не ставь следующий исполняемый этап дочерним к незавершённой инициативе, если это лишит его запуска. При QA findings верни точный дефект исходному автору через native request-changes; не заводи конкурирующую работу.

Координатор выбирает одно:
- действие — реально выполненный шаг с readback результата;
- ожидание — условие, срок и уже работающий native механизм продолжения;
- блокер — точная причина, ответственный и способ снятия.

`check_at` в тексте сам не будит. Нужны dependency, разрешённая selected delivery или существующее расписание; без этого ожидание не оформлено. Не повторяй неизменённый deny, не трогай healthy running claim. Два цикла без нового evidence требуют изменить scope/метод или заняться причиной, а не переписать статус.

Владельцу — один понятный дайджест через сохранённую доставку routine; ACK журнала/созданный файл не доказывают платформенную доставку. Не добавляй вторую ручную отправку поверх native delivery и не называй технические счётчики бизнес-результатом.
